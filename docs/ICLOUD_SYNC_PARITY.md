## 1. Account setup, identity, settings, and removal

### Setup and availability

- There is one iCloud service account per application profile, not a choice of multiple independently authenticated cloud accounts. Account creation returns the existing account if present; its local ID is fixed as `iCloud`. Both Mac and iOS disable selecting the service when it already exists. Evidence: `AM:189–213`; `Mac\Preferences\Accounts\AddAccountsView.swift:161–181`; `iOS\Settings\AddAccountView.swift:135–136`.
- Setup uses the system Apple identity, with no username/password form. Mac offers a sheet explaining cross-device feed synchronization, a use-account action, and cancel. iOS presents the analogous account sheet with an optimization-help link; successful local creation dismisses it and reports account addition. This is not a guarantee that initial cloud loading has completed: initialization starts asynchronously afterward. Evidence: `Mac\Preferences\Accounts\AccountsAddCloudKit.xib:34–63`; `Mac\Preferences\Accounts\AccountsAddCloudKitWindowController.swift:21–56`; `iOS\Account\CloudKitAccountView.swift:21–69`; `AD:685–700`.
- Before creation, both platforms check a helper described to the user as requiring iCloud Drive. The actual test is presence of `FileManager`'s ubiquity identity token, not a write test, quota test, or successful CloudKit account-status request. Failure offers a system-settings recovery action and cancel. The settings deep links are platform-specific. Evidence: `Shared\Settings\AddCloudKitAccount.swift:18–68`; `Modules\RSCore\Sources\RSCore\Platform.swift:16–18`.
- At full refresh, network absence skips the refresh. Cloud identity availability is checked separately: unavailable/restricted/signed-out states skip cloud work but continue downloading publisher feeds; one Error Log entry is posted on transition into unavailable state. An Apple account-change notification clears this condition and attempts refresh when recovering. Failure of the availability check itself permits the ordinary cloud path to run. Evidence: `AD:116–125,146–174,827–848`.
- Initial initialization creates/locates the remote root if no external root ID is stored, starts initial refresh, and subscribes to both zones. Root lookup takes the first matching account container, creates one when none is found, and even falls back to root creation for some otherwise-unhandled lookup errors. This is not a transactional singleton guarantee across concurrently initializing devices. Evidence: `AD:646–701`; `AZ:201–261`.

### Settings and defaults

- Account details expose local account name and active/inactive state; iCloud has no credentials button. The unread-content toggle is accompanied by a warning about storage, sync duration, and battery use, and an explanation that statuses and starred content are always synchronized. Evidence: `Mac\Preferences\Accounts\AccountsDetailView.swift:20–34,46–101`; `iOS\Inspector\AccountInspectorViewController.swift:25–63,153–169,209`; `ACCOUNT:131–159`.
- Account display name and active state are local account settings, not fields of the remote account container. Root container creation uses an internal root name, and received root containers are ignored as folders. Do not equate synchronized folder/feed names with synchronized account display name. Evidence: `ACCOUNT:131–159`; `AZ:201–228,316–323`; `AZD:96–104`.
- The unread-content preference is a global application preference, not per-feed or per-account. It is persisted locally and propagated to other Apple devices through the ubiquitous key-value store, separately from CloudKit records. External initial/server key-value changes update the local copy. Evidence: `AM:39–52,159–167,554–580`.
- Default/migration precedence matters: preserve an existing local value; otherwise use an already-published ubiquitous value if system identity is available; otherwise enable for an already-existing iCloud account and disable for a new installation without that account. Without system identity, default false. An absent remote key is seeded from the local setting. Consequently, “always default false” does not describe existing-user migration, and “always default true for cloud accounts” does not describe newly added accounts. Evidence: `AM:583–621`.
- The setting setter only persists/publishes the preference. It does not enumerate old articles, immediately backfill all unread content, immediately clean old cloud content, or initiate a refresh. Content decisions consult the current preference when subsequent send/cleanup work runs. Evidence: `AM:41–52`; `AD:97–102,740–747`; `RZ:148–163,191–213`.

### Local removal versus deleting synchronized data

- Account removal is confirmed as destructive in local UI. The manager refuses removal while the account is refreshing, invokes the delegate's deletion hook, deletes local settings/data, and notifies the application. The iCloud deletion hook resets both local change tokens; it does not delete cloud zones, cloud subscriptions, feeds, or articles. Re-adding can discover retained cloud data. This differs fundamentally from deleting a feed/folder within the account. Evidence: `Mac\Preferences\Accounts\AccountsPreferencesViewController.swift:68–96`; `iOS\Inspector\AccountInspectorViewController.swift:78–110`; `AM:216–239`; `ACCOUNT:564–569`; `AD:705–709`.

## 2. Synchronized model and identity

| Entity | Verified fields and relationships | Evidence |
|---|---|---|
| Root/folder container | Name and root-versus-folder discriminator. A root represents top-level membership; folders are not a recursive remote hierarchy. IDs are generated UUID record names. | `AZ:41–54,264–282,309–323`; `ZONE:119–121` |
| Subscription | Publisher feed URL, publisher title, user-edited title, homepage URL, and an array of container IDs. One subscription may belong to multiple containers. | `AZ:31–39,94–112,129–185` |
| Article status | Feed external ID plus read/unread and starred/unstarred flags. Status and content are separate records. Flags are serialized as string booleans. | `RZ:102–108,706–728` |
| Article content | Feed URL, publisher item unique ID, title, HTML/text body, article URL, external URL, summary, image URL, publication/modification dates, and author information. Authors include name, URL, avatar URL, and email. | `RZ:80–100,731–763` |
| Content ownership | Each content record references its corresponding status with server-side dependent deletion. Deleting a status therefore deletes its cloud content; deleting content alone does not delete its status. | `RZ:731–737` |

- Normal subscribe creates a deterministic subscription record name from the feed URL's MD5. OPML import instead creates UUID subscription IDs and only coalesces repeated URLs within that import call. A universal URL-derived subscription-record-ID rule would overstate upstream consistency. Evidence: `AZ:57–91,94–96,296–306`.
- Publisher-backed article identity is an MD5 derived from feed identity plus publisher unique ID, separated by a space. For parsed publisher items without a service ID, the feed URL supplies that identity. Status/content cloud IDs use separate prefixes around the same article ID. These hashes are identity mechanisms, not security promises. Evidence: `Modules\Articles\Sources\Articles\Article.swift:50–62`; `Modules\ArticlesDatabase\Sources\ArticlesDatabase\Extensions\ParsedArticle+Database.swift:13–21`; `RZ:698–703`.
- Bodies may be LZFSE-compressed into binary fields off the main thread; successful compression removes the corresponding plain body field. Receiving supports legacy plain bodies and compressed bodies; decompression failure leaves any available plain fallback. Author decoding failures are skipped. Records missing feed URL or unique item ID cannot reconstruct content and are ignored. Images are represented by URLs, not synchronized image files. Evidence: `RZ:766–786`; `RZD:122–179`.
- The reconstructed parsed item does not carry tags, attachments, language, Markdown, or a distinct thumbnail through this path; the image URL also supplies the banner-image field. The cloud path is not a complete serialization of every possible parser/article field or all application preferences. Evidence: `RZD:157–179`.

## 3. Subscription and folder mutations, OPML, and incoming tree changes

### Import and subscription creation

- OPML import parses and normalizes the document, requires a known root external ID, saves remote records, then attempts a standard refresh. It silently returns if another refresh is in progress or parsed children/root ID are unavailable; an empty document has an explicit unfinished error-handling TODO. The delegate's advertised import-in-progress property is a constant false, not a usable long-running import status. Evidence: `AD:67–68,252–285`.
- Normalization removes repeated feed URLs within the collected scope, lifts children of unnamed folders upward, and flattens nested named content toward the parent-folder representation. The cloud importer handles root feeds and immediate feeds under named folders, coalescing a repeated URL into one imported record with multiple memberships. This is not synchronization of arbitrary nested folder trees. Evidence: `Modules\Account\Sources\Account\OPMLNormalizer.swift:16–65`; `AZ:57–91`.
- Import is not verified to merge globally with existing server subscriptions by URL: its feed-record dictionary is per-call, new feed IDs are UUIDs, and new folder records are created from titles. No source evidence establishes all-or-nothing large-import transactions or import-wide deduplication against previously imported records. Evidence: `AZ:57–91,296–313`; `ZONE:670–719`.
- Normal subscription runs feed discovery and duplicate checks, downloads/parses initial content, preserves conditional-GET information, creates the remote subscription, then asynchronously queues/sends newly discovered articles and fetches article-zone changes. The provisional local feed is removed on failure. When validation is disabled, an undiscoverable feed can be stored as a dead subscription for later recovery. Some errors are broadly translated to feed-not-found or the dead-feed path; they are not all surfaced with distinct diagnoses. Evidence: `AD:938–1099`.

### Mutation outcomes and rollback

- Feed rename updates the edited title, with empty input mapped to a cleared remote edited title. Move changes the membership set by removing source and adding destination; add-to-container adds another membership without removing existing memberships. Local move/add and folder create/rename are committed after cloud success. Missing required external/container IDs are treated as account corruption. Evidence: `AD:307–327,354–395,432–478`; `AZ:116–185,264–282`.
- Feed removal is optimistic in the sidebar. Ordinary failure restores the local feed; a corruption error intentionally leaves it removed locally. At the zone level, removing the last membership deletes the subscription; otherwise it only removes that membership. Already-missing remote subscriptions count as removed. Evidence: `AD:330–351`; `AZ:129–157`.
- Important actual behavior: the higher-level removal helper discards the zone's “subscription fully deleted” Boolean and still deletes that feed's remote article-status records even if another container membership remains. Content deletion then cascades. This is an upstream coupling/limitation, not a requirement to erase shared-feed history when merely removing one membership. Evidence: `AD:1157–1188`; `RZ:171–177,735–737`.
- Folder removal first hides the local folder, queries its remote feed memberships, and removes feeds concurrently before deleting the folder record. Query failure restores the original folder. Partial feed failure restores only failed feeds, leaving successful removals gone. Failure to delete the folder after removing its feeds restores an empty folder. This is best-effort reconciliation, not a transaction spanning the folder and every feed/article. Evidence: `AD:481–560`.
- Restore-feed bypasses discovery/revalidation, optimistically reinstates the requested tree position, recreates the remote subscription from remembered metadata, updates its external ID, and rolls back locally on failure. Restore-folder creates the folder first, attempts feed restores concurrently, and logs individual failures without necessarily failing the whole restore. Neither is proof of restoration of all previously deleted cloud article records. Evidence: `AD:399–429,563–618`.

### Receiving changes and out-of-order relationships

- Incoming subscription/container deletions are processed before changed records. Feed deletion removes it from all known containers and clears conditional-GET state; folder deletion removes the local folder. Incoming root-account container changes do not create a folder or rename the local account. Evidence: `AZD:36–59,87–104,137–141`.
- Existing feeds receive metadata and membership differences. If a move's destination folder is not yet known, an existing feed remains visible at the account root until the folder arrives; arrival removes that fallback and attaches the feed to the folder. New feeds for unknown folders are held as unclaimed until the folder arrives. Evidence: `AZD:62–84,109–133,147–179,195–213`.
- Source limitation: new-feed creation returns immediately if that external ID already exists. Consequently, the new-feed path iterating several already-known memberships is not by itself proof that every membership is attached in a single incoming pass. Treat support for membership sets as model intent, not proof of bug-free reconciliation for every record order. Evidence: `AZD:77–83,182–192`.

## 4. Article statuses, optional content, and durable pending changes

### Local mutation and outbox semantics

- Marking articles first updates the local article-status database, then queues only IDs whose status actually changed. It clears account idle backoff, emits a queued-status notification, and starts a background send if total pending rows exceed 100. Read/starred state changes do not wait for cloud success. Evidence: `AD:621–641`.
- The persistent per-account `Sync.sqlite3` queue has one row per article ID and status kind. Insert-or-replace coalesces newer queued values for the same pair. A transaction selects a limited batch and marks exactly those pairs in-flight; deleting successfully sent rows only removes selected rows, allowing a newer replacement to remain pending. Pending-read/pending-starred lookups include in-flight rows. Initialization returns any previously selected rows to the queue. Evidence: `AD:104–105,683`; `Modules\SyncDatabase\Sources\SyncDatabase\SyncDatabase.swift:84–96`; `QUEUE:17–69,117–150,173–190`.
- This durable queue covers article changes, not a generalized offline queue for all subscription/folder mutations. The latter call cloud operations directly and apply the operation-specific rollback rules above. Queue insertion/reset/deletion database errors are logged internally rather than always thrown to the caller. Evidence: `AD:307–641`; `Modules\SyncDatabase\Sources\SyncDatabase\SyncDatabase.swift:35–76`.
- Publisher refresh queues newly discovered unread articles as new, updated articles as new-record updates, and removed articles as deletions. Newly materialized articles that already have a read status are deliberately not treated as genuinely new. Evidence: `AD:1102–1134,1233–1240`.
- Sending processes batches of up to 150 queue rows, groups them by article ID, fetches current local articles, builds updates, sends, acknowledges selected rows, and continues. Failure resets selected rows and logs the error. A completely unusable batch has its selected rows discarded and stops processing. Failed queue selection is currently treated as no work by `try?`, a source limitation. Evidence: `SEND:19,84–142`.

### Content/status decision rules

For a grouped outgoing update, deletion wins. A lone new-record marker uses the create-if-new path. Otherwise a locally available starred article, or an unread article when unread-content syncing is enabled, sends status plus content; everything else sends status and deletes any cloud content record. If content is required but the local article is absent, update construction fails. When a status-only update has no article, fallback status is read and unstarred; the individual queue flags are not independently replayed as complete article state. Evidence: `SU:27–75`; `RZ:194–215`.

| State/action | Required observable outcome | Source |
|---|---|---|
| Starred, whether read or unread | Synchronize status and attempt to preserve/upload content regardless of unread-content toggle. | `SU:49–55`; `RZ:151–154,419–427` |
| Unstarred unread, toggle on | Synchronize status and upload content on applicable new/update sends. | `RZ:155–160,201–209`; `SU:53–55` |
| Unstarred unread, toggle off | Synchronize status; do not require new content upload. Ordinary status-only updates remove existing cloud content; cleanup can remove old leftovers. | `RZ:155–163,210–213,419–428` |
| Unstarred read | Preserve/synchronize status; ordinary status-only updates delete cloud content. This is not article/status deletion. | `SU:49–58`; `RZ:210–213` |
| Article deleted | Delete cloud status; dependent cloud content is deleted with it. | `SU:41–43`; `RZ:208–209,735–737` |
| Cloud content deleted alone | Do not delete the receiving device's locally downloaded article or its status. | `RZD:69–79` |

- On the ordinary update path, status writes and content deletions are submitted first, then create-if-new records, then optional content writes. Optional existing-content upload failure is logged but does not roll back successfully sent statuses or force requeuing them. This avoids one oversized optional article invalidating ordinary status updates. However, the create-if-new collection contains both new statuses and their content; it is not the same isolation guarantee for every new-record failure. Evidence: `RZ:194–239`; `SEND:125–142`.
- Receiving statuses protects locally pending changes independently per field: incoming read changes cannot overwrite pending local read changes; incoming star changes cannot overwrite pending local star changes, including in-flight changes. It is not a global pending-article lock. Evidence: `RZD:57–63,82–101`; `QUEUE:173–190`.
- A received status deletion deletes the local article unless that article has a pending star-kind change; pending read alone does not protect it. The guard checks existence of a pending star change, not specifically a pending `starred=true` value. Content-record deletion notifications are intentionally ignored by local deletion processing. Evidence: `RZD:69–79`.
- Received content is decoded off-thread, grouped by feed URL, and merged with `deleteOlder:false` after status changes are applied. A partial received content set is therefore not treated as an authoritative complete publisher feed. Any deletions returned by that local merge are queued for synchronization. Evidence: `RZD:94–113`.

## 5. Retention: distinguish local database, cloud content, and cloud statuses

These are different policies. A permanent tombstone for every old local article, a cloud-content purge, and forgetting old read-state are not interchangeable.

| Policy | Verified behavior | Evidence |
|---|---|---|
| Local article retention | iCloud uses the same feed-based retention category as local accounts. On nonempty publisher-feed updates, remove articles only if unstarred, absent from the current feed, and locally arrived more than 30 days ago. Unread alone does not exempt an old absent article. Starred articles are exempt. | `ACCOUNT:323–324`; `Modules\ArticlesDatabase\Sources\ArticlesDatabase\ArticlesTable.swift:210–215,252–274` |
| Old newly encountered publisher items | Incoming items published more than 183 days ago default to read when status rows must be created. Missing publication dates do not automatically count as old. Existing statuses remain meaningful. | `Modules\Articles\Sources\Articles\ArticleStatus.swift:16`; `Modules\ArticlesDatabase\Sources\ArticlesDatabase\ArticlesTable.swift:229–238` |
| Partial cloud-content receive | Does not run the publisher-completeness deletion rule because `deleteOlder:false`. | `RZD:103–107`; `ACCOUNT:933–940` |
| Local status pruning | At startup, feed-based accounts prune unstarred statuses older than 30 days only when no corresponding local article exists, irrespective of read flag. Startup also removes articles/statuses for unsubscribed feeds, but that helper returns without action when the subscribed-feed set is empty. | `Modules\ArticlesDatabase\Sources\ArticlesDatabase\ArticlesDatabase.swift:422–435`; `Modules\ArticlesDatabase\Sources\ArticlesDatabase\ArticlesTable.swift:605–650`; `ACCOUNT:345–349` |
| Cloud content cleanup | Always keep starred content; delete unstarred read content, plus unstarred unread content when the toggle is off, and orphaned content. This does not itself delete cloud statuses. | `RZ:419–428,456–480` |
| Cloud stale-status classification | Unstarred and cloud record creation date older than 183 days; unread status may also qualify. This is not publication age, last-change age, or local arrival age. | `RZ:21,431–445,595–632`; `Modules\Articles\Sources\Articles\ArticleStatus.swift:16` |

## 6. Cloud storage statistics and cleanup UX

### Scan semantics and presentation

- A real remote scan counts status records and content records separately, each partitioned into starred, unstarred unread, and unstarred read. These categories are exclusive: a starred unread article is in starred, not also unread. Orphaned content is included in the displayed read-content count. Counts describe records, not bytes, quota utilization, unique subscriptions, or counts of locally cached articles. Evidence: `RZ:354–409,595–686`; `STATS:12–32`.
- Scan status records first using only read/star keys, then content references, following pagination and reporting partial counts per page. The completed scan caches status metadata and content-reference mappings for five minutes for potential cleanup reuse. Body download is unnecessary for these statistics. Evidence: `RZ:60–72,354–409,595–686`.
- The model distinguishes idle, fetching, completed, canceled, and error. Starting/restarting resets displayed counts and cleanup state; serial numbers suppress old scan callbacks/results after cancel or restart. Cancel preserves the partial values but does not pretend the scan completed. Missing iCloud account produces a specific error. Evidence: `VM:10–49,176–219`.
- Mac starts scanning on first appearance, presents scan success/cancel/failure, supports refresh/cancel and shareable text, highlights cleanup-eligible read content and unread content when disabled, and reports incomplete counts plus an error alert on scan failure. iOS uses a retained shared view model, starts only when idle, provides equivalent sections and refresh/cancel/share/help, and cancels work on entering background. Evidence: `MAC-STATS:48–93`; `Mac\CloudKitStats\Scan\CloudKitStatsScanViewController.swift:81–177`; `IOS-STATS:14–16,20–163`.
- Optimization help is an external documentation link available from account setup/details and the stats UI. Mac stats live in a reusable nonresizable dedicated window; iOS exposes stats through settings troubleshooting when an iCloud account exists. Native sharing sheets, icons, window chrome, and browser presentation are platform mechanisms rather than sync requirements. Evidence: `Modules\Account\Sources\Account\CloudKit\CloudKitWebDocumentation.swift:10–12`; `Mac\CloudKitStats\CloudKitStatsWindowController.swift:11–41`; `iOS\Settings\SettingsViewController.swift:211–216,307–310`; `MAC-STATS:81–93`.

### Cleanup eligibility and execution

- Cleanup is enabled after a completed scan if its plan is nonempty or a prior cleanup made the plan stale, and not while already cleaning. The plan includes read-content counts and, only when unread-content sync is off, unread-content counts. Although stale-status count exists in the data model, plan total and displayed deletion total deliberately exclude stale statuses. Evidence: `STATS:27–48,59–68`; `VM:130–143`.
- Cleanup requires destructive confirmation. Fresh confirmation lists planned content-category counts and warns about duration; stale confirmation describes applicable content categories without promising old exact counts. Starred content is not a deletion category. Evidence: `MAC-STATS:95–118,203–225`; `IOS-STATS:80–87,282–307`.
- Manual cleanup reuses a valid five-minute scan cache, otherwise scans fresh mappings. It invalidates the cache and deletes eligible records by category in batches of 400, reporting phases and cumulative deleted counts. At this revision, neither the manual entry point nor its public UX deletes stale statuses, despite helper support for that phase. Evidence: `RZ:22,273–351`; `AD:740–747`.
- UI shows active phase, progress, per-category deleted totals, cancel, completed/canceled states, return to old scan results, and a fresh-scan action. Cleanup error explains that some work may already have succeeded and suggests waiting/retrying/refreshing, rather than promising rollback. Completion/cancel/error marks the old plan stale; old scan numbers are not automatically decremented into newly authoritative statistics. Share output switches to cleanup result counts when that screen is active. Evidence: `VM:158–170,221–251`; `MAC-STATS:77–93,190–200`; `Mac\CloudKitStats\CleanUp\CloudKitStatsCleanUpViewController.swift:70–145`; `IOS-STATS:167–224`.
- Automatic content cleanup is not an independent daily timer. It is invoked near the end of the account's status-sync path. First eligible invocation only seeds the last-cleanup date. Later invocations run only when that date is more than six days old; the date is advanced before work, even if cleanup fails, to avoid repeated expensive failures. The incremental pass scans all statuses, then content until finding at most 400 deletable records. Evidence: `AD:177–207,1193–1228`; `RZ:248–267,486–503,529–557`.
- Cancellation and concurrency limitation: scan pagination records handler errors/cancellation but does not cancel the underlying CloudKit query chain immediately. Manual cleanup loops do not explicitly check cancellation between every batch, and model cleanup callbacks lack the scan serial-number guard. A cancel action is therefore not verified to stop all in-flight/remaining network work immediately or to prevent every late progress callback. Cached eligibility is a snapshot, not an atomic recheck against another device starring an article during cleanup. Evidence: `ZONE:177–241,878–905`; `RZ:273–351`; `VM:214–251`.

## 7. Refresh ordering, triggers, scheduling, and push

### What a refresh actually does

1. A standard full refresh clears account idle backoff and retrieves account-zone changes.
2. If account-zone retrieval has not failed, receive article/status-zone changes.
3. Refresh publisher feeds locally, even if cloud work failed.
4. On standard refresh, send pending article changes only when earlier cloud stages have not failed. Initial refresh deliberately skips this explicit final send.
5. Record completion/progress/activity; propagate the remembered cloud error after the publisher refresh if necessary.

Evidence: `AD:817–825,850–934`. The receiver operation catches its own fetch error and logs activity failure instead of throwing it outward, so the high-level “skip following cloud work on error” intent is not a universal guarantee for article-receive errors. Likewise, sending can report `didFail` without throwing from its operation wrapper. Evidence: `RECEIVE:33–55`; `SEND:53–75`; `AD:1137–1153`.

### Trigger matrix

| Trigger | Verified behavior |
|---|---|
| New account/root initialization | Find/create root, initial full refresh without final explicit status send, subscribe to account and article zones. `AD:683–700,817–825`. |
| Explicit full refresh / scheduled feed refresh | Fetch tree, receive statuses/content, fetch publisher feeds, send queued statuses; network/availability checks and degraded publisher-only mode apply. `AD:146–174,850–934`. |
| Periodic status synchronization | Send queued statuses, receive article-zone changes, evaluate idle backoff, potentially clean content. It does **not** fetch account-zone changes in this method. `AD:177–207,233–249`. |
| User changes read/star | Local update/outbox, clear account backoff, notify status timer, opportunistic send above 100 pending rows. `AD:621–641`. |
| Publisher refresh discovers/updates/deletes articles | Queue new/update/delete markers; full refresh normally sends after fetching feeds. `AD:1102–1134,1233–1240,913–921`. |
| A feed is newly subscribed | Background queue/send of its initial articles and article-zone fetch after subscription creation. `AD:1028–1040,1068–1099`. |
| Remote cloud notification | Clear account idle backoff, enqueue notification processing, inspect zones and fetch matching-zone changes; not a full publisher refresh or an unconditional outbox send. `AD:128–143`; `PUSH:32–59`; `ZONE:127–139`. |
| Recovery from unavailable Apple account | Clear unavailable flag and attempt full refresh if previously unavailable. `AD:116–125`. |
| iOS foreground | Resume if necessary; refresh feeds if the last refresh was over 15 minutes ago, otherwise status sync. `iOS\AppDelegate.swift:169–204`. |
| iOS background transition | Invalidate foreground status timer, request background feed work, start status sync under a bounded OS background task, wait for work, then suspend/save. `iOS\AppDelegate.swift:178–197,277–329,331–382`. |
| Mac termination | Save, attempt final status send while pumping run loop for up to two seconds; not guaranteed unlimited flush. `Mac\AppDelegate.swift:342–357`. |

- Shared status timer normally schedules every 120 seconds, backs off to 1,800 seconds when all active accounts report no meaningful work, and exits idle mode on queued-status notification. Cloud account status sync has its own 30-minute no-change suppression. A failed send prevents marking that account quiet, though the shared timer uses the returned `didWork` Boolean, not `didFail`, so failure behavior across both layers is not a perfect immediate-retry guarantee. Evidence: `Shared\Timer\ArticleStatusSyncTimer.swift:15–24,59–106`; `AM:366–384`; `AD:177–207`.
- Source limitation: status-sync work detection consults delegates' last-page changed/deleted counts, while article refresh separately accumulates counts across pages for activity messages. Account-zone last counts may be stale because status-only sync does not fetch that zone. Do not treat returned work/idle as a mathematically exact changed-record count. Evidence: `AD:194–221`; `RZD:29–56`; `RZ:123–138`; `AZD:27–29,36–38`.
- Feed refresh cadence is a separate user setting: manual, 30 minutes, one hour, two hours, four hours, or eight hours. Manual disables the feed timer, not the status timer. Mac feed timer skips while system sleeping and can suspend/resume a due refresh. Evidence: `Shared\Timer\RefreshInterval.swift:11–33`; `Shared\Timer\AccountRefreshTimer.swift:42–69,88–107`.
- Mac registers for silent remote notifications independently of visible notification permission; notifications are forwarded to active accounts. Its release launch generally fires both feed and status refresh unless sync-on-launch suppression is set; debug launch schedules timers instead. Evidence: `Mac\AppDelegate.swift:248–274,326–330`; `AM:307–310`.
- iOS schedules OS-managed background feed refresh with an earliest start one hour later, not a promised hourly execution time. Expiration cancels the task, and completion is guarded to happen once. Push delivery resumes/suspends account processing and reports new data even though inner zone fetches can log and swallow errors. Evidence: `iOS\AppDelegate.swift:116–123,391–469`; `ZONE:127–139`.

**Parity implication for a polling-only transport:** status polling must eventually obtain subscription/folder changes as well as article changes, or the absence of Apple's subscription-zone push changes the observable feature set. Two-minute polling alone does not cover initial hydration, manual refresh, post-subscribe send, foreground/background/exit opportunities, idle recovery, or bounded retry behavior.

## 8. Conflict, recovery, partial failures, and progress

- CloudKit stores separate private account and article zones in the application's Apple container. Server change cursors are local preferences scoped by zone name/owner. Change retrieval processes one page, awaits local delegate application, saves that page's cursor only afterward, and follows more-coming pages. This supports resuming after suspension without requiring one giant in-memory transaction. Evidence: `AD:42–48`; `AZ:51–54`; `RZ:113–118`; `ZONE:94–116,741–807`.
- Expired change tokens are removed and retrieval restarts. A missing zone is created and the request retried. A user-deleted account zone is different: ordinary full refresh clears the local subscription tree and logs an error; user-facing recovery asks to remove/re-add the application account. Article-zone refresh and article modification instead have explicit recreate-and-retry paths for a deleted article zone. Evidence: `ZONE:19–31,828–850`; `AD:884–896`; `RZ:123–138,689–695`.
- General mutations use changed-key saves and atomic requests, not a source-defined Lamport clock, per-device snapshot protocol, CRDT, or explicit fieldwise total-order merge. Changed-key saves avoid replacing unrelated fields, but a membership-array update still writes an entire computed array; concurrently changed membership elements are not proven to be merged without loss. Evidence: `ZONE:629–641`; `AZ:129–185`.
- There is no universal application-defined “read wins,” “unread wins,” “star wins,” “deletion wins,” or timestamp/device tie-breaker. Incoming read and star values are independently suppressed only while a matching local kind is pending, including in-flight rows; after that protection ends, subsequent incoming server values are applied. Remote status deletion is suppressed by any pending star-kind row, but not a pending read row. Outgoing status records write **both** read and star values from the current local article, even if only one kind initiated the send; changed-key policy therefore does not imply one-field-only status writes. No source-defined total order guarantees which concurrently accepted remote update will ultimately be received. Evidence: `RZD:57–101`; `QUEUE:173–190`; `RZ:706–728`.
- New-record saves use optimistic “server unchanged” policy with non-atomic operation. Server conflicts are recognized by the shared resolver, but there is no general three-way conflict-merging routine here. The create-if-new helper treats an otherwise-unclassified partial failure as success; that can hide individual new-record/content failures, so “all new records confirmed stored” would be stronger than this source. Evidence: `ZONE:373–443`; `RESULT:45–55`.
- Rate-limit/service-unavailable/zone-busy retry uses the server retry delay only when present. General modify additionally retries direct network failures three times at three-second intervals. Limit-exceeded operations split recursively into smaller saves/deletes, fail if a single remaining record cannot fit, and may commit earlier chunks before later failure; whole-logical-operation atomicity is not preserved by splitting. Evidence: `RESULT:33–38`; `ZONE:14–15,405–439,666–730`.
- Partial failures prioritize expired token, missing zone, deleted zone, and account-unavailable/authentication errors; otherwise they remain partial failures. General modify does not share save-if-new's blanket success treatment. Quota, permission, and other errors are user-describable through the CloudKit error wrapper, not special conflict resolution strategies. Evidence: `RESULT:47–81`; `ZONE:651–730`; `Modules\CloudKitSync\Sources\CloudKitSync\CloudKitError.swift:20–96`.
- Per-record failures during change/query enumeration can be omitted by `try?` while the surrounding operation continues. Full-rescan-on-token-expiry does not explicitly compare all existing local objects against a complete server manifest to remove anything missing. There is no verified universal integrity repair or arbitrary-corruption recovery promise. Evidence: `ZONE:188–194,762–768,845–848`; `AZD:36–59`.
- Progress combines publisher-feed and sync progress. Activity Log records operation lifecycle, per-page counts, sends including content counts, remote notification receipt, scans, and cleanup. Error Log entries carry account identity, operation, detailed error, and source location. Some receiver/notification/optional-content failures are activity/system-log-only, so not every failure propagates identically to the UI. Evidence: `AD:74–93,652–680,773–790`; `SEND:45–75`; `RECEIVE:38–55`; `RZ:228–239`; `ACCOUNT:1211–1214`.

## 9. Provider-independent outcomes versus Apple mechanisms

| Preserve as behavior/UX | Apple-specific mechanism, not itself a OneDrive requirement |
|---|---|
| Clear system-identity prerequisite and recovery; distinguish unavailable identity from unavailable internet; continue publisher fetching when cloud identity is unavailable. | Ubiquity identity token, CloudKit account-status API, Apple settings URLs, Apple account-change notification. |

## 10. Integration requirements against the stated OneDrive scope

The following compares only the implementation scope reported in the task: OS-signed-in OneDrive folder transport; device-owned Lamport/device LWW snapshots with per-field values; durable outbox/tombstones; local publisher fetching and OPML; starred-plus-optional-unread content; two-minute polling without push; account settings and local-only removal. No parent implementation was inspected or validated.

1. **Retention is additional to content selection.** Verify 30-day absent-from-feed local article retention with starred exemption, 183-day default-read handling for old newly encountered items, and separate startup pruning of orphan local statuses. Do not silently interpret the cloud stale-status classifier as an active cloud-status expiry policy; both exposed cleanup callers disable it. See section 5.
2. **Stats/cleanup is a complete user-facing feature, not just garbage collection.** The stated scope does not establish a remote status/content record scan, exclusive category counts, orphan accounting, progress/cancel/error states, share/help, destructive cleanup confirmation, stale-plan handling, or category totals. Manual cleanup is distinct from bounded six-day automatic cleanup. See section 6.
3. **Defaults and preference propagation need explicit parity decisions.** Optional unread bodies default off for a genuinely new setup but preserve existing preferences and migrate existing iCloud users differently. Upstream shares this preference across devices outside the main record store. No evidence in the stated scope establishes equivalent sharing/migration. Toggling alone does not require immediate backfill. See section 1.
4. **Trigger coverage exceeds a fixed polling interval.** Verify initialization hydration, manual full refresh, subscriptions/tree changes in polling, local read/star wake-up from idle, opportunistic queue flush, post-subscribe article upload, publisher change queueing, lifecycle/exit opportunities, account/network recovery, and retry/backoff. Without push, timely tree-change polling is especially important. See section 7.
5. **Status correctness must be independent of body availability.** Ensure pending local read/star changes are protected independently; receiving content deletion must not erase a local article; deleting status is a different action; failed optional bodies must not block durable status delivery. A generic content tombstone cannot substitute for an article/status deletion tombstone. See sections 4 and 8.
6. **LWW is a declared semantic difference until checked.** Upstream uses changed-key server operations and pending-local-field protection, not Lamport/device LWW. Per-field snapshots may preserve intended outcomes, but source inspection cannot establish equivalence for membership concurrency, deletion versus pending starring, absent/cleared edited names, restore, or partial folder failure. Record these as acceptance scenarios rather than claiming upstream defines that protocol. See sections 3, 4, and 8.
7. **OS folder availability is not proof of completed cloud persistence.** Upstream distinguishes local mutation, pending queue, successful server operation, and remote receive. Folder-transport-specific meaning of pending/uploaded/caught-up is outside this source specification; UX must not imply a verified server acknowledgement merely from a local filesystem write. This is an integration boundary, not a proposal to adopt Graph or app registration.
8. **Recovery/removal boundaries must stay explicit.** Local account removal retains remote data. Re-adding should hydrate rather than globally purge. Lost local receive state, deleted provider storage, unavailable system identity, quota/permission failures, and partial imports/mutations need truthful errors and recovery paths; permanent tombstones must not accidentally convert local cleanup/removal into global data loss. See sections 1, 3, 5, and 8.
9. **Preserve metadata and relationships, not only public API names.** Verify user-edited versus publisher titles, root versus folder membership, multiple memberships, feed/homepage URLs, publication/modification dates, HTML/text, authors, summaries/images/links, and merge of partial content sets. Do not invent recursive-folder or full-attachment parity that upstream lacks. See sections 2–4.
10. **Observability is part of parity.** Expose distinction between feed refresh and synchronization, meaningful pending/error/progress states, incomplete scans, partial cleanup success, and account-level activity. A successful poll with no network transfer is not by itself proof of cross-device convergence. See sections 6–8.

## 11. Verification boundaries and source limitations

- This is static source evidence, not a live CloudKit service experiment, timing benchmark, OS-account validation, or OneDrive integration test. The CloudKitSync test file inspected is a placeholder smoke-test skeleton, not behavioral proof: `Modules\CloudKitSync\Tests\CloudKitSyncTests\CloudKitSyncTests.swift:1–12`.
- No claim is made of total-order conflict resolution, exactly-once operations, atomic multi-zone/multi-chunk transactions, immediate cancellation of network operations, guaranteed push delivery, guaranteed background scheduling, immediate preference-triggered backfill, or complete repair after arbitrary record loss.
- Notable source-level caveats are intentionally retained in this specification: root-creation fallback after lookup errors; UUID imports versus deterministic normal-subscribe IDs; partially successful folder deletion/restore; membership removal deleting article history even when another membership remains; pending-star-kind rather than only pending-star-true deletion protection; swallowed receive/content errors; broad partial-success handling for new records; last-page idle accounting; snapshot cleanup races; and helper support for stale-status deletion that exposed callers do not enable.
- Requirements should reproduce user-visible outcomes and explicitly chosen compatibility behavior, not blindly preserve these weaknesses or silently describe stronger guarantees than the upstream code provides.
